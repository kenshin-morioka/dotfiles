# ドキュメントレビュースキル

設計書・仕様書PRの表記・フォーマット・視認性を観点別にチェックし、優先度付きで報告する。

## Step 1: 対象の取得

優先順:

1. 引数にPR URL/番号 → `gh pr view <num/url> --json title,body,files,headRefName,baseRefName`
2. 引数なし → 現在のブランチに紐づくPR
3. PRが無い → ローカル変更（`git diff` / `git diff --cached`）

差分本体は `gh pr diff <num>` か `git diff <base>...HEAD` で取得。Markdown 以外のファイル（`.rb` などのコード）は本スキルの対象外（必要なら `/code-review` を案内する）。

末尾改行・末尾 `|` の有無など **diff 表示で見えない問題** を確実に拾うため、対象ファイルの**実体**も `git show <ref>:<path>` で個別に確認する。

## Step 2: 観点別チェック

各観点について差分と実体を照合し、該当があればメモする。**該当なしの観点は報告しない**。

### A. 誤字・用語

- **同義語の表記揺れ**: 同じ概念が別表記で混在していないか（例: 「単価UP」と「単価アップ」、「ユーザ」と「ユーザー」）
- **複合語の前後入れ替え**: 「A（B）」と「B（A）」のように括弧と本体が入れ替わっていないか。ユビキタス言語など正準定義があればそちらに揃っているか
- **複数識別子を1つのバッククォートに詰める**: `` `a, b` `` のように1つのコードスパンに複数語が入っていないか。`` `a` `` / `` `b` `` に分割すべき
- **明らかな誤字脱字**

### B. テーブル・Markdown 構文

- **テーブル末尾の `|` 欠落**: 行末が `|` で閉じていない行は、その列以降が崩れて描画される
- **末尾改行欠落**: `\ No newline at end of file` が出ているファイル
- **HTMLエスケープの残骸**: 本文中の `&gt;` `&lt;` `&amp;` `&quot;`。Markdown 本文/テーブルセル内では生文字でよい
- **テーブル列幅の不一致による視覚崩れ**: 新規追加行が既存行と幅が極端に違う場合は揃える（描画には影響しないが diff レビュー時に読みづらい）
- **コードフェンス未閉じ・言語指定漏れ**

### C. スタイル統一

複数の類似ドキュメント（同じディレクトリの兄弟ファイル等）が PR に含まれる場合、**同じ意味の項目が同じ構造で書かれているか**を相互比較する:

- 同じセクション（例: 認証・権限チェック）の記述が、ファイルごとに段組み/箇条書き構造が違う
- 同じバリデーションエラーの説明文が、ファイル AB で別表現になっている（例: `a が b 以前` vs `b >= a`）
- 表セル内の句点有無が、行ごとに統一されていない
- 同じカラム説明列で、ある行だけ詳細が抜けている / 別の行だけ実装詳細が混入

### D. 視認性

- **括弧開始の文**: 箇条書きや段落が `（…）。〜` で始まると主語が取れない。体言/動詞で書き始める
- **1文に複数論点**: 要望 / 方針 / 補足 / 例外 等を1文に詰めている場合は箇条書きに分解
- **言語混在**: mermaid/コード例/表説明で、周囲は日本語なのに1行だけ英語ラベル（またはその逆）
- **見出し直後の余分な空行**: 兄弟ファイルと空行数が揃っていない（実害は薄いが読みやすさに寄与）
- **画像のみで本文説明なし**: 図がある場合、本文に最低限の言語的説明があるか

### E. 内部リンク・参照

- 相対リンクの URL エンコード（`%5B` `%5D` 等）が壊れていないか
- 外部リンク（Notion / Slack 等）の URL が体裁通りに貼られているか
- 設計書の場合、ユビキタス言語・関連仕様書への相互リンクが張られているか

## Step 3: 優先度付け

検出項目を以下で分類:

- **High**: 描画が崩れる / 情報が欠落する（テーブル末尾 `|` 欠落、リンク切れ、ユビキタス言語からの直接的な逸脱）
- **Medium**: 表記揺れ・スタイル不統一（同義語混在、エラー説明の表現違い、HTMLエスケープ残り）
- **Low**: 視認性改善（句読点・空行・1文分割・図への補足）

## Step 4: レポート出力

```markdown
# {PRタイトル or 対象} レビュー結果

## 1. 誤字・用語の揺らぎ
### 1-1. {見出し} {ファイル名}:{行}
```
{該当箇所の引用}
```
→ {具体的な修正案}

## 2. フォーマットの不備
### 2-1. {見出し}【優先度高】
（同上）

## 3. 視認性
### 3-1. {見出し}
（同上）

---

優先して直すべきは **{番号}**、次点で **{番号}** です。
```

注意点:
- **該当なしのカテゴリは丸ごと省略する**（「該当なし」とは書かない）
- 指摘は**ファイルパスと行番号**を必ず添える
- 修正案は**具体的に**（「統一する」ではなく「`単価UP` に統一する」）
- 構造に関する所見（節題の選び方など、レビュアー裁量の領域）は最後に「補足: 構造に関する所見（参考）」として分離して提示する
- コードロジックや仕様妥当性のレビューはしない（範囲外と明示）
