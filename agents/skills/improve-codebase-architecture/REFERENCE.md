# リファレンス

## 依存カテゴリ

深化の候補を評価する際、その依存を分類してください：

### 1. インプロセス

純粋な計算、インメモリ状態、I/Oなし。常に深化可能 — モジュールを統合して直接テストするだけです。

### 2. ローカル代替可能

ローカルのテスト代替物がある依存（例：Postgres用のPGLite、インメモリファイルシステム）。テスト代替物が存在すれば深化可能。深化されたモジュールは、テストスイートでローカル代替物を実行してテストします。

### 3. リモートだが所有（Ports & Adapters）

ネットワーク境界を超える自社サービス（マイクロサービス、内部API）。モジュール境界にポート（インターフェース）を定義します。深いモジュールがロジックを所有し、トランスポートは注入されます。テストではインメモリアダプタを使用。本番では実際のHTTP/gRPC/キューアダプタを使用します。

推奨の表現形式：「共有インターフェース（ポート）を定義し、本番用HTTPアダプタとテスト用インメモリアダプタを実装することで、ネットワーク境界を超えてデプロイされていても、ロジックを1つの深いモジュールとしてテストできるようにする。」

### 4. 真の外部（Mock）

制御できないサードパーティサービス（Stripe、Twilio等）。境界でモックします。深化されたモジュールは外部依存を注入されたポートとして受け取り、テストではモック実装を提供します。

## テスト戦略

基本原則：**レイヤーを重ねるのではなく、置き換える。**

- 浅いモジュールの古いユニットテストは、境界テストが存在すれば無駄 — 削除する
- 深化されたモジュールのインターフェース境界で新しいテストを書く
- テストは内部状態ではなく、パブリックインターフェースを通じた観測可能な結果をアサートする
- テストは内部リファクタリングに耐えるべき — 実装ではなく振る舞いを記述する

## 依存戦略

該当するカテゴリと依存の扱い方：

- **インプロセス**: 直接統合
- **ローカル代替可能**: [具体的な代替物]でテスト
- **Ports & Adapters**: ポート定義、本番アダプタ、テストアダプタ

## テスト戦略

- **書くべき新しい境界テスト**: インターフェースで検証する振る舞いを記述
- **削除すべき古いテスト**: 冗長になる浅いモジュールのテストをリスト
- **テスト環境の要件**: 必要なローカル代替物やアダプタ
