# コードベースのアーキテクチャ改善

AIの視点でコードベースを探索し、アーキテクチャ上の摩擦を表面化させ、テスタビリティ改善の機会を発見し、モジュール深化リファクタリングをRFCとして提案します。

**深いモジュール**（John Ousterhout著「A Philosophy of Software Design」）は、大きな実装を隠す小さなインターフェースを持ちます。深いモジュールはよりテストしやすく、AIがナビゲートしやすく、内部ではなく境界でテストできます。

## プロセス

### 1. コードベースの探索

Agentツールの `subagent_type=Explore` を使用して、コードベースを自然に探索してください。固定的なヒューリスティックに従うのではなく、有機的に探索し、摩擦を感じた箇所を記録してください：

- 1つの概念を理解するために、多くの小さなファイルを行き来する必要がある場所はどこか？
- インターフェースが実装とほぼ同じくらい複雑な、浅いモジュールはどこか？
- テスタビリティのためだけに純粋関数を抽出したが、本当のバグはそれらの呼び出し方に潜んでいる場所はどこか？
- 密結合のモジュールが、モジュール間の繋ぎ目で統合リスクを生み出している場所はどこか？
- コードベースのどの部分がテストされていないか、またはテストしにくいか？

あなたが経験する摩擦こそがシグナルです。

### 2. 候補の提示

深化の機会を番号付きリストで提示してください。各候補について以下を示します：

- **クラスタ**: 関連するモジュール/概念
- **結合の理由**: 共有型、呼び出しパターン、概念の共同所有
- **依存カテゴリ**: 4つのカテゴリについては [REFERENCE.md](REFERENCE.md) を参照
- **テストへの影響**: 境界テストに置き換えられる既存テスト

この段階ではインターフェースの提案はしないでください。ユーザーに「どれを詳しく検討しますか？」と聞いてください。

### 3. ユーザーが候補を選択

### 4. 問題空間の整理

サブエージェントを起動する前に、選択された候補の問題空間について、ユーザー向けの説明を書いてください：

- 新しいインターフェースが満たすべき制約
- 依存する必要がある依存関係
- 制約を具体化するための大まかなコードスケッチ — これは提案ではなく、制約を具体的にするためのもの

これをユーザーに提示し、すぐにステップ5に進んでください。サブエージェントが並列で作業している間、ユーザーは問題空間を読んで考えます。

### 5. 複数のインターフェースを設計

Agentツールを使って3つ以上のサブエージェントを並列で起動してください。各サブエージェントは、深化されたモジュールの**根本的に異なる**インターフェースを設計します。

各サブエージェントに個別の技術ブリーフ（ファイルパス、結合の詳細、依存カテゴリ、何を隠蔽するか）を渡してください。このブリーフはステップ4のユーザー向け説明とは独立しています。各エージェントに異なる設計制約を与えてください：

- エージェント1: 「インターフェースを最小化 — エントリーポイントを1-3個に抑える」
- エージェント2: 「柔軟性を最大化 — 多くのユースケースと拡張をサポート」
- エージェント3: 「最も一般的な呼び出し元に最適化 — デフォルトケースを簡単にする」
- エージェント4（該当する場合）: 「境界をまたぐ依存にはPorts & Adaptersパターンで設計」

各サブエージェントの出力：

1. インターフェースシグネチャ（型、メソッド、パラメータ）
2. 呼び出し元の使用例
3. 内部に隠蔽する複雑さ
4. 依存戦略（依存の扱い方 — [REFERENCE.md](REFERENCE.md) 参照）
5. トレードオフ

設計案を順番に提示し、その後に文章で比較してください。

比較後、あなた自身の推奨を述べてください：どの設計が最も優れていると考えるか、その理由は何か。異なる設計の要素を組み合わせるとよい場合は、ハイブリッド案を提案してください。意見を持ってください — ユーザーが求めているのはメニューではなく、強い見解です。

### 6. ユーザーがインターフェースを選択（または推奨を受け入れる）

### 7. RFCの作成

[REFERENCE.md](REFERENCE.md) のテンプレートを使用して、リファクタリングRFCを作成してください。

RFCの保存先は、プロジェクトのルール（CLAUDE.md等）に記載があればそれに従ってください。記載がなければユーザーに確認してください（GitHub Issue、リポジトリ内ファイル、その他）。作成前にユーザーのレビューを求めないでください — 作成して保存先を共有してください。
