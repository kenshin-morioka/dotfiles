# 共有文書の作成・編集

## 書き込みは承認があるときだけ

共有文書（Notion、Google Docs、Claude Docs、Artifact、Slack canvas など）への書き込みは、ユーザーの明示的な指示があるときだけ行う。

- 「提案して」「案を出して」「一緒に書いていこう」は、チャットに案を出す指示。文書には書かない
- 案への指摘（「テーブルの方が良い」「この行は不要」）は修正指示。直した案をチャットに返す。承認ではない
- 自分が出した「判断してほしいこと」に回答が来ていない間は、書かない
- 書くのは「書いて」「反映して」「Notion に記載して」のように書き込みを明示されたときだけ。承認の範囲（どの節か）を超えて書かない
- 既存文書を書き換える前に、消える内容を確認する。構造変更や削除は、何を消すかを先に伝える
- 書いた後は再取得して、意図どおりになっているかを確認する

承認なしに書いた場合は、ユーザーの信用を失う重大なルール違反として扱う。気づいた時点で元に戻し、その旨を報告する。

## 本文の書き方

読む人のコストを下げる。情報は内容だけにする。

- 冒頭に「更新日 / 整理者 / 書き方の方針」のようなメタ行を書かない。更新日や作成者は文書ツールのプロパティにある
- 目次ブロックを入れない
- 見出しに「1. 」のような番号を付けない
- 各項目は 1 行で、事実 + 参照リンクの形にする。「〜という状況である」のような説明の重複を削る
- 参照は「…（`[link](url)`）」で各項目の末尾に付ける。出典が同じ項目が並ぶなら、節の冒頭に「出典: …」と 1 回だけ書く。「（同上）」を繰り返さない
- Notion のページを参照するときはページメンションを使う。節番号を指す場合はメンションの後にテキストで添える（例: `<mention-page/> D7`）
- 確定情報と未確定・推測を混ぜない。未確定は「未定」「未確認」と明記する
- 時系列、比較、項目 × 属性はテーブルにする。並列の事実は箇条書き、短い結論は文で書く
- 文は短く、1 文 1 内容。読む人が知らない略語は初出で展開する

## 進め方

1. 対象文書を取得し、既存の見出し構成と書式を把握する
2. 案をチャットに出す。判断してほしい点（粒度、含める範囲、形式）があれば案と一緒に挙げる
3. 指摘があれば案を直してチャットに返す。承認があるまで 2〜3 を繰り返す
4. 承認された範囲だけを書き込み、再取得して確認し、書いた場所を URL で報告する

## 要求整理と要件定義の書き分け

要求整理は「確定している事実の整理」、要件定義は「それを受けて何を作るかの合意」。前者は事実と参照だけ、後者は判断を含む。

### 要求整理

- 確定情報だけを書く。契約書・議事録・資料・Slack の発言など、原典があるものに限る
- 節は「案件 / 契約 / 現状の業務 / 顧客と合意済みの事項 / 範囲 / セキュリティ・データ / 開発方針 / 体制 / 資料」程度。案件に合わせて増減する
- 1 項目 1 行、末尾に参照。根拠のない推測・提案・今後の方針は書かない
- 古い資料（ドラフトで締結されなかった要件書など）は根拠にしない。契約書がある項目は契約書の条番号を参照にする

### 要件定義

見出しごとの粒度とフォーマット。

| 節 | 書くこと | 形式 |
| --- | --- | --- |
| 経緯 | 契約・MTG・体制変更など、今の状態に至った出来事を時系列で。粗い事実のみ | テーブル（時期 / 出来事）。参照列は置かず、出典は参考資料へ |
| ステークホルダー | 組織ごとの人物と役割、組織間の関係。役割は 1 語〜数語で、作業内容を書かない | mermaid の flowchart TB。組織を subgraph、関係を矢印。固定色は使わない（ダークモードで読めない） |
| 期限 | 契約上・合意上の期日と、その日に何が起きるか | テーブル（期限 / 内容）。未確定の時期は「中旬」のような幅のまま書く。合意ではなく提案に基づく内容は「※」で背景を添える |
| 参考資料 | 原典のリンク一覧。種類ごとに分ける | 種類ごとにトグル（顧客向け資料 / 契約 / 顧客データ / 社内の整理 / コード / Slack など） |
| 目的 | 顧客に対して達成すること。目標値（削減率など）が契約・合意にあれば数値で書く。開発方針（汎用化など）も目的に含めてよい | 結論を 1 文 + 箇条書き |
| スコープ: やること | 扱う範囲の境界。契約の実施内容・対象・展開順・成果物。粒度は粗く、機能の具体は書かない | 箇条書き 5〜8 行 |
| スコープ: やらないこと | 契約の対象外、顧客環境への配備、他部署展開など。「作らない」判断には理由を添える | 箇条書き。理由は同じ行に |
| 機能要件 | 利用者の操作の流れ順に「〜できる」で書く。実現手段（OCR、画面、LLM など）は書かず、何ができるかだけ | 操作の流れごとの小見出し + 箇条書き。理由が要る項目は 1 階層下に |
| 非機能要件 | 提供環境、セキュリティ、データ保持、性能、可用性・運用、汎用性。契約から導けるものに条番号を付ける。根拠のない数値目標は置かない | 小見出し + 箇条書き |
| 懸念事項 | 確認待ちの事項と、未決の分担。誰に何を確認するかまで書く | 箇条書き |

### 判断の根拠

- 実装の進み具合や既存コードの状態を根拠にスコープや要件を決めない。契約書・顧客への説明資料・合意事項を根拠にする
- 契約の成果物名と社内の用語が違うときは、初出で「社内用語（契約上の名称は〜）」と結び、以後は社内用語で統一する
- 契約・顧客向け資料・PoC 実装のどれにもない機能は、要件に入れず「やらないこと」に理由つきで書く。SaaS 化・汎用化を難しくする機能は特に
- 自分が出した案に「判断してほしいこと」を付けるときは、各項目に推奨を添える。回答がない項目は推奨のまま進めず、確認する

### 表記の統一

- 業務の対象（販売実績 / 実績データ など）、出力物（基幹取込用 CSV など）、利用者（担当者 / 利用者 など）は文書全体で 1 つの語に揃える
- 書き終えたら揺れている語を洗い出し、統一案を表にして提示してから直す

### 基本設計と詳細設計の境界

基本設計は「何を、どの構成要素が、どう受け渡すか」まで。手順・画面項目・API のパラメータ・テーブル定義のような「どう作るか」は詳細設計に回し、基本設計には書かない。

| 項目 | 基本設計 | 詳細設計へ |
| --- | --- | --- |
| システム構成 | 構成要素と責務、依存の向き（mermaid） | 技術選定の細部、ライブラリ |
| 処理フロー | 主要な流れと、AI を使う箇所・決定論の箇所 | アルゴリズム、例外の分岐 |
| 画面設計 | 画面一覧と遷移、各画面の役割 | 画面項目、バリデーション、文言 |
| データ設計 | 主要エンティティと関係 | テーブル定義、カラム、インデックス |
| エンドポイント設計 | リソース単位の一覧と役割 | パラメータ、レスポンス、エラーコード |
| ジョブ・スクリプト | 何をいつ動かすかの一覧 | 実装、再試行条件 |
| 外部連携 | 入出力ファイルの種類と受け渡し、外部サービスに送るデータの範囲 | 列仕様、API 呼び出しの形 |
| インフラ設計 | 構成要素、ネットワーク境界、認証・テナント分離の方式 | IaC、パラメータ |
| 運用設計 | 監視・バックアップ・復旧の方針 | 手順書、閾値 |
