# PRレビュー指摘対応スキル

PRで受けたレビュー指摘に対して、コード修正とチェックリスト更新をセットで行う。

## Step 1: レビュー指摘の収集

引数にPR URLがあればそのPRを、なければ現在のブランチに紐づくPRを特定する。

```bash
gh pr view --json number,url,author
```

PRのレビューコメントを取得する:

```bash
gh api --paginate repos/{owner}/{repo}/pulls/{number}/comments --jq '.[] | {path, line, body, user: .user.login}'
gh api --paginate repos/{owner}/{repo}/pulls/{number}/reviews --jq '.[] | select(.body != "") | {body, user: .user.login, state}'
```

## Step 2: 対応が必要な指摘の特定

収集したコメントから、以下を除外する:

- bot（devin-ai-integration等）のコメント
- 純粋な質問・確認のコメント。語尾（「〜ですか？」等）ではなく意図で判定し、疑問形でも具体的な修正を求めていれば対象に含める。判断に迷うものはユーザーに確認する
- 既に「Resolved」「対応済み」等で解決済みのコメント
- PR作成者自身のコメント（`author.login` と `user` を照合する）

残ったコメントを「コードの改善を求める指摘」として一覧化する。

## Step 3: コード修正

各指摘に対して修正を行う。

- 指摘の意図を正確に理解してからコードを修正する
- 指摘が曖昧な場合はユーザーに確認する
- 修正後にテストを実行して動作確認する

## Step 4: 指摘の抽象化

各指摘について、以下の観点で抽象化する:

1. **この指摘は何のケースか？** — 具体的なコード（例: "VC APIのループが不要"）ではなく、一般原則（例: "外部APIの制約を事前確認していない"）に昇華する
2. **どのプロジェクト・言語でも当てはまるか？** — 当てはまるなら `default.md`、特定技術スタックに依存するなら該当チェックリスト
3. **既存のチェック項目と重複しないか？** — 既存項目でカバーできるなら追加不要
4. **既存のチェック項目と矛盾しないか？** — 矛盾する場合は、両方の項目を提示し、どちらを採用すべきかユーザーに質問する（勝手に上書きしない）

抽象化した結果をユーザーに提示し、確認を得る:

```markdown
## 抽象化結果

| # | 元の指摘 | 抽象化したチェック項目 | 追加先 |
|---|---------|-------------------|-------|
| 1 | {具体的指摘} | {一般原則} | {対象チェックリスト} |

- 既存項目でカバー済み: {スキップした指摘とその理由}
```

**ユーザーの確認を得てから Step 5 に進む。**

## Step 5: チェックリストの更新

`~/.claude/checklists/` 配下の該当ファイルに項目を追加する。

- 既存の項目群の中で、意味的に近い項目の近くに配置する
- チェックリスト内の既存の文体・粒度に合わせる
- 追加した項目には具体例を添えない（抽象的な原則のみ。具体例が必要なレベルの項目は粒度が細かすぎる可能性がある）

## Step 6: 結果報告

```markdown
## 対応結果

### コード修正
- {修正内容のサマリー}

### チェックリスト更新
| チェックリスト | 追加項目 |
|--------------|---------|
| {ファイル名} | {追加した項目} |

チェックリスト以外にルール（.claude/rules/）への反映が必要と思われる指摘があればここで提案する。
```
