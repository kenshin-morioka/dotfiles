# テスト駆動開発

## 哲学

**基本原則**: テストは実装の詳細ではなく、パブリックインターフェースを通じた振る舞いを検証すべきです。コードは完全に変わっても、テストは壊れるべきではありません。

**良いテスト**はインテグレーション型です。パブリックAPIを通じて実際のコードパスを実行します。システムが**何をするか**を記述し、**どのように実装しているか**は記述しません。良いテストは仕様書のように読めます。「有効なカートでチェックアウトできる」というテスト名は、どんな機能が存在するかを正確に伝えます。これらのテストは内部構造を気にしないため、リファクタリングに耐えます。

**悪いテスト**は実装に結合しています。内部のコラボレータをモックしたり、プライベートメソッドをテストしたり、外部手段で検証したりします（インターフェースを使う代わりにデータベースに直接クエリするなど）。警告サイン：リファクタリングしたらテストが壊れたが、振る舞いは変わっていない場合。内部関数をリネームしてテストが失敗するなら、そのテストは振る舞いではなく実装をテストしています。

テストの良い例・悪い例は [tests.md](tests.md) を、モックのガイドラインは [mocking.md](mocking.md) を参照してください。

## アンチパターン: 水平スライス

**全テストを先に書いてから、全実装を書くのは絶対にやめてください。** これは「水平スライス」であり、REDを「全テストを書く」、GREENを「全コードを書く」として扱っています。

これは**質の低いテスト**を生み出します：

- 一括で書かれたテストは**実際の**振る舞いではなく**想像上の**振る舞いをテストする
- ユーザー向けの振る舞いではなく、データ構造や関数シグネチャなどの**形状**をテストしてしまう
- テストが実際の変更を検知できなくなる — 振る舞いが壊れてもパスし、振る舞いが正しくても失敗する
- 実装を理解する前にテスト構造にコミットしてしまう

**正しいアプローチ**: トレーサーバレットによる垂直スライス。1つのテスト → 1つの実装 → 繰り返し。各テストは前のサイクルで学んだことに基づきます。コードを書いたばかりなので、どの振る舞いが重要で、どう検証すべきかを正確に把握できます。

```text
間違い（水平）:
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正しい（垂直）:
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## ワークフロー

### 1. 計画

コードを書く前に：

- [ ] ユーザーに必要なインターフェース変更を確認する
- [ ] ユーザーにテストすべき振る舞いを確認する（優先順位を付ける）
- [ ] [深いモジュール](deep-modules.md)の機会を特定する（小さなインターフェース、深い実装）
- [ ] [テスタビリティ](interface-design.md)のためのインターフェースを設計する
- [ ] テストすべき振る舞いをリストアップする（実装手順ではなく）
- [ ] ユーザーの計画承認を得る

質問：「パブリックインターフェースはどうあるべきですか？テストすべき最も重要な振る舞いは何ですか？」

**全てをテストすることはできません。** どの振る舞いが最も重要かをユーザーと明確に確認してください。テストの労力はクリティカルパスと複雑なロジックに集中させ、あらゆるエッジケースに費やさないでください。

### 2. トレーサーバレット

システムに関する1つのことを確認する1つのテストを書きます：

```text
RED:   最初の振る舞いのテストを書く → テスト失敗
GREEN: テストを通す最小限のコードを書く → テスト成功
```

これがトレーサーバレットです — パスがエンドツーエンドで機能することを証明します。

### 3. 反復ループ

残りの各振る舞いについて：

```text
RED:   次のテストを書く → 失敗
GREEN: テストを通す最小限のコード → 成功
```

ルール：

- テストは一度に一つ
- 現在のテストを通すのに必要なコードだけ
- 将来のテストを先回りしない
- テストは観測可能な振る舞いに集中する

### 4. リファクタリング

全テストが通った後、[リファクタリング候補](refactoring.md)を探します：

- [ ] 重複の抽出
- [ ] モジュールの深化（複雑さをシンプルなインターフェースの背後に移動）
- [ ] SOLID原則の自然な適用
- [ ] 新しいコードが既存コードについて明らかにすることを検討
- [ ] 各リファクタリングステップ後にテストを実行

**REDの状態ではリファクタリングしない。** まずGREENにしてください。

## サイクルごとのチェックリスト

```text
[ ] テストは実装ではなく振る舞いを記述している
[ ] テストはパブリックインターフェースのみを使用している
[ ] テストは内部リファクタリングに耐える
[ ] コードはこのテストに対して最小限である
[ ] YAGNI - 不要な機能を先回りして追加していない
```
